# Bounty QA Checker (tukang periksa)

The QA checker is a separate agent from the builder. Its only job: try to make the entry FAIL the way the grader would, before the grader gets the chance. It reports to the lead (Arsi); it never edits entry code, never submits, never talks to the user directly.

## Core rules

1. **Independence**: the checker must not be the session that wrote the code. If it built it, it cannot check it.
2. **Test like the grader**: replicate the grader's exact conditions — same command line, same flags, same resource limits (1 CPU via `taskset -c 0`, cold caches), same input/output paths. "Works on my run" is not evidence.
3. **Evidence or it didn't happen**: every pass/fail claim cites a command + observed output (exit code, byte count, hash, timing). No vibes.
4. **Report, don't fix**: list defects with severity (blocker / major / minor) and the exact repro. The lead decides what to fix and sends it back to a builder.
5. **Adversarial mindset**: assume the entry is broken until proven otherwise. The three round-1 rejections we took (starter main.ts, script-generated data, `python3 -P` import failure) were all catchable pre-submit.

## Universal checklist (every bounty)

- [ ] Rules re-read from the kit (competition.yaml / RULES) — caps, deadlines, formats, submit limits.
- [ ] Determinism: run the entry twice, diff outputs/hashes — must be byte-identical.
- [ ] Size caps measured, not estimated (file bytes, dossier bytes, screenshot bytes, snapshot bytes).
- [ ] Transcript pre-flight:
  - Entrypoint (main.ts/main.py) contains agent-authored lines (not byte-for-byte starter).
  - Large data files were written via write/edit tool, not generated by a script.
  - Entrypoint (or code it runs) took final content from ≥2 write/edit messages (`thinking_revised`).
  - Usage rows exist for the builder session(s) in `~/.makefun/muse-usage-<slug>.jsonl`, valid JSON per line, newline-terminated.
- [ ] No secrets, claim codes, or keypair material in any output/log/file.
- [ ] Kit is the latest version (re-downloaded this session; rules+snapshot compared — cite the comparison, not just "checked").
- [ ] Quota/final-entry: `can_submit` true for this bounty and submit count within limits; if the bounty uses final-entry selection, the intended final entry is the one picked.

## By bounty type

### Score / perf bounties (forge, csv-speed, solvers)
- [ ] Benchmark under 1-CPU cap with cold caches; compare vs house baseline and #1's known perf.
- [ ] Profile the dominant operation; name the top 3 hot spots with numbers.
- [ ] Stress edge cases: empty input, huge input, malformed input — no crash, no hang.

### Elo / game-bot bounties (chess)
- [ ] Perft exact on standard positions.
- [ ] Match vs previous version (≥20 games): new version must not lose.
- [ ] Worst-move time under 1 CPU stays well within limits at the chosen node cap.
- [ ] Packed size ≤ cap with margin (report exact bytes after compress — main session runs compress, checker verifies).

### Program / image bounties (news-image, passport)
- [ ] Run EXACTLY as grader: `MAKEFUN_OUTPUT_DIR=<dir> python3 -P -s <entry>/main.py` from a different cwd → exit 0.
- [ ] Output PNG: dimensions ≤1024×1024, bytes ≤1 MiB; smaller is better (tie-break).
- [ ] Look at the image: read every word/date/number for errors; check dates against research notes.
- [ ] No local-module imports in main.py (the `-P` trap).

### Judge / web-app bounties (GTA, radar, trophy, cover art)
- [ ] Run the app headless; zero console errors.
- [ ] Screenshot every required view; LOOK at each screenshot — list the first 3 visual defects.
- [ ] All interactive controls exercised (buttons, filters, detail views) — nothing dead.
- [ ] Dossier ≤1.5 MiB, dashboard text ≤65,536 bytes, screenshots within byte/dimension caps.
- [ ] Content accuracy spot-check vs sources (dates, names, numbers).
- [ ] Data/model claims verified, not asserted: fitted models show held-out error vs the previous version (radar v2 lesson: 87.7% vs 150.2%); verdict counts (FARM/WATCH/SKIP) reconcile with board row count.
- [ ] Game bounties: play 3 minutes headless/scripted — missions completable, no soft-lock, wanted/traffic systems behave (see action-wanted-system, urban-road-traffic skills).

### Chess/perf addendum (chess v3 lesson)
- [ ] NPS measured under `taskset -c 0`; node cap chosen so worst-move time stays within server budget with margin.
- [ ] Packed size re-measured AFTER final compress; compress shown in an uploaded session after the source's last write.

No submit until the adversarial suite passes with 0 crashes/timeouts.

## Speed rules (EL's order, 2026-11-21)

- **Smoke first**: run the cheapest fatal-defect checks first (imports, one game/position, tiny benchmark). If smoke fails, report immediately — don't burn 30 minutes on a full match for a broken entry.
- **Full tests in background**: long matches/benchmarks run as background processes while you do the remaining checks; poll the log, don't block on them.
- **Reuse harnesses**: use the repo's `tests/` harness; if you adapt or write one in /tmp, copy the working version back into `tests/` so the next checker starts warm.
- **Parallel-friendly**: your checks should be splittable — the lead may run two checkers in parallel (e.g., one on perft/bench, one on matches). Keep your harness files and logs in distinct paths.

## Report format (to the lead)

```
QA VERDICT: PASS / FAIL (n blockers)
Checklist: <item> — PASS/FAIL — <evidence: command + result>
Defects:
  [BLOCKER] <what> — repro: <command> — expected vs actual
  [MAJOR] ...
  [MINOR] ...
Perf (if applicable): <metric> before/after, 1-CPU conditions
Residual risks: <what could not be verified locally>
```

## Process (EL)

- The lead spawns the checker after the builder reports done, before compress/check/submit.
- If the checker finds a blocker, the lead sends it back to a builder session for a fix, then re-checks.
- Security notices during QA still need EL's fresh explicit approval — the checker stops and reports, the lead asks.
- The checker's session may be included in the transcript bundle as evidence of verification work when useful.

## Verification Loop — Regression Test on Every Fix (EL, 2026-11-22)
Whenever QA finds a gap or bug, the Builder must add **1 new regression test case** to the local test script/harness (in the repo's `tests/`) that reproduces the found failure, BEFORE any final optimization. The fix is only accepted when the new case passes AND the full existing suite still passes — a fix must never break functionality that already passed. QA re-runs the whole suite (old + new cases) before issuing [VERDICT QA: LULUS].
